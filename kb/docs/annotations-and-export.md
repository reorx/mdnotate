# 标注与导出

写给要改划词高亮、评论、标注侧栏或导出模板的人：标注是什么、什么时候会被丢弃、界面各部分为什么长成现在这样。

## 数据模型

highlight 与 comment 是同一结构，`comment === null` 即纯高亮。界面区分两者，数据层不区分；「Annotate」只是 UI 文案，数据层只有 comment。

锚点是**渲染文本的字符偏移**（`start` / `end`）加一份 `quote`。这决定了后面几乎所有的约束：任何改动渲染文本节点的做法都会让偏移错位。

## 什么时候标注会被丢弃

每条标注存一份创建时的文档内容哈希。打开文档时哈希不匹配的标注直接删除，并提示丢弃了几条。

`annotationContentHash` 是「原文哈希 + 渲染版本」：原文没变、渲染出的文本变了，偏移一样会错位。纯文本只有原文哈希，docId 计算不变。Markdown 目前有三个版本后缀：

- `:front-matter-v1`，只加在含已闭合 Front Matter 的文档上：元数据从普通 Markdown 改成字段列表，旧布局的标注走失效机制删除。
- `:list-numbers-v1`，加在所有 Markdown 上：有序列表编号成了文字（见 `reader-ui.md`）。要知道一篇文档有没有有序列表得先解析它，而对没有列表的文档，下面的挪动什么也不改，所以不区分。旧标注不丢弃，见下文「编号成为文字之前的标注」。

- `:obsidian-images-v1`，仅加在正文实际解析出 Obsidian 图片嵌入的 Markdown 上，位于列表版本之后。旧布局中的嵌入文字变成图片，旧标注直接走失效提示，不进入仅迁移列表编号的分支。检测和渲染共用语法规则，代码示例、转义与 YAML 元数据里的嵌入不会触发；打开与编辑保存都使用同一个 `annotationContentHash`。

图片组件的占位、图片和错误提示始终位于 `not-annotatable` 子树，加载状态变化不影响偏移或搜索索引。

原因：偏移是对渲染文本数出来的，文件在外部被改过就会全部错位；而标注库按偏移恢复高亮时**不校验 quote**，会静默高亮到错的句子。宁可丢弃也不高亮错。

剪切板文档的 id 本身就是内容哈希，天然永远匹配。

在 app 内编辑并保存是例外：标注还在手上，保存后按每条标注的原文在新文本里重新定位，只有原文不再原样出现的才丢弃。规则与时机见 `editing.md`。

另一条丢失路径是 Recent 的 50 条上限：标注行挂在 Recent 条目上并随它级联删除，文档被挤出 Recent 时标注一起销毁。这是明确选择的行为。

### 编号成为文字之前的标注：挪，不丢

这一次的渲染变化可以精确撤销：旧文本就是新文本去掉编号节点。所以哈希等于 `preListNumbersHash(当前哈希)` 的标注不丢弃，而是：

1. 打开时 `splitStaleAnnotations` 把它们单独分出来（`legacy`），连同旧哈希一起进 store，`annotationsHash` 停在旧哈希上，标注层不启用。
2. 正文渲染后，Reader 收集带编号标记的文本节点（`collectAnnotatableSegments`），`moveOntoListNumbers` 把每个旧偏移映射到新偏移：恰好从某项开头起的标注不吞进该项编号，跨项的标注吞进中间的编号，quote 按新文本重读。
3. 先写 store 再写库（hash、quote、偏移一起改），标注层随之启用。

旧偏移处的文字和 quote 对不上的标注照常丢弃并提示 —— 那说明它不是在这份文本上做的。若库里同时有新旧两种哈希（上一次挪动只写了一半），旧的那批直接丢弃：两批偏移数的是不同的文本，放不进同一个 store。

## 读写规则

- **改标注只走 `annotate` 这一个漏斗**：先写 store 后写库，写库失败只出提示。
- 写入是 upsert，只更新 comment 和更新时间。quote 与偏移在提交那一刻就固定了；唯一的例外是它们下面的文本变了的时候（保存编辑、编号成为文字），由 `rebaseAnnotations` 一起改写。
- **打开时标注必须与文档同时进 store。** 文档和恢复的标注一次性写入，避免先启用标注层、再恢复旧偏移。阅读期间显式导入的新增条目会追加到现有高亮层，保留选区、滚动位置和侧栏评论草稿。
- **标注层的 key 是 `docId#contentHash`，不能只写 docId。** 同一个文档被重开是常态（刷新按钮、双击已开着的文档、Recent 里点回来），此时 docId 不变、正文却可能已被换掉。只按 docId 建 key，标注层会留在原地，继续按旧偏移在新正文上画高亮。内容没变时哈希不变、标注层不重建，草稿、选区、滚动位置全部原地保留 —— 这是刷新一个没被改过的文件时的正常结果。

## 标注库（recogito）的约束

- 必须用 `SPANS` renderer。
- 库在鼠标松开时**立即创建 draft**。未提交的 draft 要在选区移动、外部点击、关闭弹窗时删除。
- 我们自己放在标注容器里的层（弹窗、评论图标）都要带 `not-annotatable` class。库在这类元素内的点击会直接返回、不清空选区。
- 程序化打开弹窗和点高亮是同一条路径：都经过库的选中状态变化。
- 已有高亮的弹窗按高亮元素（`[data-annotation]`）的矩形定位。
- 封装里弹窗状态有 ref 和 state 两份，必须同步写入：事件回调读的是 ref，渲染读的是 state。
- 改主题时用 `setStyle()` 热更新样式，不要重建标注层，那会丢掉草稿和选区。

## 弹窗

新划的选区先给 Highlight / Annotate 两个按钮。点已有高亮直接进评论输入框 —— 弹窗只有一种编辑态，没有只读态。

- Enter 保存，Shift+Enter 换行，Esc 与点外部一律**丢弃**改动。
- 保存空串 = 退回纯高亮。
- 底部左边删除、右边 → / 取消 / 确认，都是纯图标，所以 `title` 和 `aria-label` 两个都得给。`IconButton` 把这件事包死，不要手写裸 `<button>`。
- 输入框本身是 `CommentEditor`，弹窗和侧栏共用：按键、按钮、含义两边完全一致。

### → 按钮：挪到侧栏去写

弹窗挂在选区下方，会盖住紧接着的正文，没法边看边写。→ 把正在写的东西交给侧栏：

- 新选区先提交成标注：框里有字就带着评论，空的就是纯高亮。已有的标注，内容变了就先存。
- 然后关弹窗、打开侧栏、该条目设为 active，条目里的输入框打开并聚焦。框里是**原样**的文字（不 trim），写到一半带着末尾空格挪过去也能接着打。
- Enter / Esc 的判定要避开输入法组字，见 `reader-ui.md` 的「键盘与输入法」。

### 落点

标注层只交出「锚点矩形 + 可视区」，落点由纯函数决定：下方装得下就挂在下方，装不下翻到选区上方，两边都不够就取空间大的那边，再把整张卡片钳进可视区。宁可盖住一点正文，也不留半截弹窗。

卡片尺寸是量出来的，不是写死的：工具栏和编辑器宽度不同，从工具栏换成编辑器时高度也会变。量完再定位，量之前那一帧不会被画出来。

可视区来自正文滚动容器，跳转到某条标注时用的也是同一个 —— 「谁是滚动容器」只声明一次。

## 正文里的评论图标

带评论的高亮末尾有一个小图标，落在高亮最下面那行的最右端。

图标层是标注容器内**自己的一层**，不能塞进库的高亮层：那层每次重画都整个清空重建，而且整层带混合模式，图标颜色会被混掉。

同步靠库的重绘事件（滚动、resize、状态变化后都会发），位置从高亮元素的矩形现算。两个必配套项：

- 重绘事件每个滚动帧都发，更新状态前必须比较一次新旧位置，否则滚动全程重渲染。
- 加 / 删评论不移动任何矩形，光靠重绘事件的时序不保险，另有一个随标注变化触发的兜底。

## 标注侧栏

右侧栏默认隐藏，新增标注时自动打开，顶栏最右的按钮是开关。

- 条目按文档顺序。store 里的标注本来就是排好序的，不要在组件里再排一次。
- 点击条目跳转到正文。滚动容器要显式传给库 —— 库自己是从标注容器往上找第一个真的在滚动的祖先。
- 哪一条算 active 由两个来源合成：侧栏里点了谁、正文里打开了哪个弹窗。后者优先，点高亮时侧栏的标记要跟着走。
- 条目的引用文字是素的，不带正文里那层琥珀底。一整列全是引用，刷成一片琥珀之后这个底色就不再意味着「这是高亮」。active 由边框、浅底和序号颜色表示。
- 有评论的条目，图标放在评论行首，不放引用行末尾：引用最多显示三行，被截断时行尾的东西会跟着被裁掉。

### 在侧栏里写评论

- 条目右上角的铅笔（无评论时是加号）在 hover、active、键盘聚焦时出现，点它先跳到正文对应位置，再在条目里打开输入框。
- 条目是两个并排的控件：跳转是一个 `<button>`，输入框在它外面 —— button 里放不了 textarea。边框和底色挂在外层。
- 同一时间只有一个条目在编辑，状态在 Reader（`listEditor`），换文档时清掉。
- 和弹窗不同，**点外部不关**：在侧栏写的意义就是边看正文边写，点正文、选字复制都不该丢掉草稿。只有 Enter / ✓ 保存、Esc / × 放弃会关。
- 保存和删除不依赖标注层还活着：源码视图、编辑模式下标注层已销毁，改动直接进 store，标注层重建时从 store 取。（这两种模式下侧栏是 `inert`，实际点不到，但不靠这一点。）

## 导出

导出是两层模板：

- 外层 `settings.template`：占位符 `{{filePath}}`、`{{annotations}}`。
- 内层 `settings.annotationTemplate`：占位符 `{{highlight}}`、`{{comment}}`，默认是 `> {{highlight}}\n{{comment}}`。

条目之间恒定隔一个空行。

内层**按行**渲染，两条规则各解决一个问题：

1. **一行里的占位符全空，则整行丢弃**（连同行内的字面文字）。所以同一个模板既能写纯高亮也能写带评论的，纯高亮不会拖一个空行。
2. **多行的值会把本行开头的引用 / 缩进标记补到自己每一行前面。** 所以 `> {{highlight}}` 引的是整段，而不只是第一行。

渲染成空的条目会被跳过，否则条目之间会多出一个空行。

## 导入默认格式的标注

先展开阅读器右侧的 Annotations 侧栏，标题与总数右侧提供 Import 按钮；没有标注时显示总数 0，仍可导入。粘贴默认模板导出的 Markdown，点击 Preview 核对每条引用、评论和处理结果，再导入有效条目；取消不写入。导入层覆盖阅读器，正文快捷键暂停，下面的侧栏评论草稿继续保留。源码视图、编辑模式与标注重新定位期间不能导入；换文档或内容变化会清掉旧面板，修改输入后要重新预览。

支持可选路径标题、纯高亮、多行引用和多段评论。路径标题只作说明，始终导入当前文档。每条引用行只剥离默认导出加上的一层 `> `，保留字面 Markdown、空格、标点和嵌套引用；只统一 CRLF / CR 为 LF，不渲染或规范化引用文字。引用中的空行应为默认导出的 `> ` 行。

定位用可标注正文的原样文本，和高亮层数偏移的规则一致：Front Matter 字段与列表编号参与定位，图片加载提示和其它 `not-annotatable` 内容不参与。引用唯一匹配才可导入；找不到、多处出现（包括重叠匹配）和格式错误分别显示原因，不猜位置。同一位置、引用、评论都相同的条目在已有标注和本批次中去重；相同引用的不同评论各自保留。

默认导出没有 ID、时间和位置，恢复的条目会得到新 ID 与时间。它也没有转义条目边界：空行后出现引用行会被当作下一条，评论内部不带分隔空行的引用行会报格式问题；连续引用行也无法普遍区分是引用还是评论。条目分隔和文件尾部的空行会被移除，不能据此恢复评论末尾的空行。预览用于核对这些边界，不能承诺任意历史评论无损往返，也不支持自定义模板。

提交时重新检查文档身份、渲染文本、可标注状态和已有条目，避免过期预览或重复点击产生错误写入。导入只追加，立即显示高亮、评论图标和侧栏，可直接跳转、编辑、删除和再导出。持久化沿用现有单条写入，没有批量事务：部分失败时明确显示已保存和未保存数量，失败条目留在当前页面，并提示离开前导出保留副本。异步写入始终绑定提交时的文档，不会改写后来打开的文档。
